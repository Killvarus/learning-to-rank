# Подробный разбор: обучение ранжированию на поисковых запросах

## 1. Задача

Пользователь вводит запрос «wooden coffee table», поиск должен показать сверху самые подходящие товары. Обучение
ранжированию (learning to rank, LTR) — построить функцию `score(запрос, товар)`, по которой товары сортируются.
Важен **порядок внутри запроса**, а не абсолютные значения: оценки товаров разных запросов между собой не сравниваются.

### Данные: WANDS

Wayfair ANnotation DataSet (Chen et al., ECIR 2022) — разметка поиска мебельного магазина:
- 480 запросов, 42 994 товара (название, класс, путь в каталоге, описание, характеристики, рейтинг);
- 233 448 пар «запрос — товар», оценённых асессорами: **Exact** (полностью подходит), **Partial** (частично),
  **Irrelevant**. Переводим в оценки релевантности 2 / 1 / 0;
- на запрос в среднем 486 оценённых товаров (медиана 217, максимум 4 329).

Такие датасеты собирают так: из логов поиска берут запросы, для каждого — кандидатов из текущего поиска, и отдают пары
асессорам (в Яндексе — через Толоку). Асессоры работают по инструкции с примерами, каждую пару смотрят несколько
человек, итог — по голосованию с учётом их надёжности.

## 2. Как мерить качество: NDCG

```
DCG@k  = Σ_{i=1..k} (2^rel_i − 1) / log2(i + 1)
NDCG@k = DCG@k / IDCG@k          (IDCG — DCG идеального порядка)
```

- `2^rel − 1` даёт Exact (3) втрое больше веса, чем Partial (1);
- `1 / log2(i + 1)` — чем ниже позиция, тем меньше она важна: пользователь смотрит в основном первые строки;
- нормировка делает метрику сравнимой между запросами (у одних запросов много подходящих товаров, у других мало).

Ещё метрики: **MRR** — 1 / позиция первого Exact; **P@10** — доля Exact в первой десятке.

**Тонкость с ничьими.** Если модель выдаёт одинаковые оценки, порядок решает сортировка, и константа может «ранжировать»
по порядку строк в файле — а он бывает неслучаен. Мы разбиваем ничьи случайно с фиксированным seed (есть тест).

### Протокол

5-fold **GroupKFold по запросам**: запросы test-фолда модель не видела вообще. Это имитирует главное требование
к поиску — работать на новых запросах. Если делить пары случайно, модель увидит другие товары того же запроса и
оценка завысится. Итоговые числа — среднее по пяти фолдам ± стандартное отклонение. Для сравнения моделей —
парный критерий Уилкоксона по запросам (одни и те же запросы у обеих моделей).

## 3. Признаки

Все признаки считаются по текстам каталога и запросов, **без меток релевантности**, поэтому их можно посчитать
один раз для всех пар — утечки между фолдами нет ([src/ltr/features.py](src/ltr/features.py)).

### BM25 — главный классический признак

```
score(q, d) = Σ_{t ∈ q} idf(t) · tf(t, d) · (k1 + 1) / (tf(t, d) + k1 · (1 − b + b · |d| / avgdl))
idf(t) = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
```

- **idf** — редкое слово («ottoman») важнее частого («table»);
- **насыщение по tf** (k1 = 1,2): десятое повторение слова почти ничего не добавляет, в отличие от TF-IDF;
- **нормировка длины** (b = 0,75): длинное описание не выигрывает просто за счёт объёма.

Реализован с нуля ([src/ltr/text.py](src/ltr/text.py)): веса всех слов во всех документах считаются один раз в
разреженную матрицу, тогда оценка пары — скалярное произведение строки этой матрицы и мешка слов запроса. Тест сверяет
результат с формулой на игрушечном корпусе. BM25 считается отдельно по названию, классу, категории, описанию,
характеристикам и всем полям вместе — поля разной важности, и модель сама решает, как их взвешивать.

### Остальные группы

| группа | признаки | зачем |
|---|---|---|
| lexical | косинусы TF-IDF по словам и по символьным 3–5-граммам | символьные n-граммы ловят опечатки и словоформы («sofas» ↔ «sofa»), как FastText |
| overlap | доля слов запроса в названии / классе / категории / описании, все ли слова есть, входит ли фраза целиком | простые и очень сильные сигналы точного совпадения |
| qclass | совпадение класса запроса (поле в датасете) с классом товара, похожесть строк классов | класс запроса — результат классификатора запросов, такой признак есть в любом продовом поиске |
| meta | длины полей, рейтинг, число отзывов | качество и популярность товара |
| semantic | LSA (SVD-150 над TF-IDF), BERT | смысловая близость без точного совпадения слов |

**BERT** — `sentence-transformers/all-MiniLM-L6-v2`, би-энкодер: запрос и «название | класс» товара кодируются
независимо в векторы 384, оценка — косинус. Модель не дообучалась (zero-shot). Векторы товаров считаются один раз
(43 тыс. за ~6 минут на CPU) и кэшируются.

## 4. Три подхода к LTR

### Поточечный (pointwise)

Каждую пару рассматриваем отдельно и решаем регрессию `score → rel`. Просто, работает любая модель (линейная регрессия,
лес, бустинг), но лосс не знает, что сравниваются товары одного запроса: ошибиться на 0,5 у пары из «лёгкого» запроса
так же дорого, как у пары из «трудного», а ошибка, не меняющая порядок, всё равно штрафуется.

### Попарный (pairwise)

Учимся правильно упорядочивать пары товаров одного запроса. **RankNet** (Burges, 2005):

```
P(i выше j) = σ(s_i − s_j),     loss = −log σ(s_i − s_j)   для пар с rel_i > rel_j
```

Модель — MLP над признаками. Пар в запросе бывает сотни тысяч, поэтому на шаге берём случайные 2 000.
XGBoost `rank:pairwise` — то же на деревьях.

### Списочный (listwise)

Оптимизируем качество всего списка.
- **ListNet** (Cao et al., 2007): «вероятность быть первым» `softmax(s)` против `softmax(rel)`, кросс-энтропия.
- **LambdaMART** (LightGBM `lambdarank`, XGBoost `rank:ndcg`): градиент попарного лосса умножается на |ΔNDCG| —
  насколько изменился бы NDCG, если поменять два товара местами. Ошибки наверху списка стоят дороже ошибок внизу.
  Формально попарный, но оптимизирует списочную метрику, поэтому обычно его относят к списочным.

## 5. Результаты и как их читать

| подход | модель | NDCG@10 |
|---|---|---|
| бейзлайн | случайный порядок | 0.542 |
| бейзлайн | BM25 по названию | 0.730 |
| бейзлайн | **BM25 по всем полям** | **0.805** |
| бейзлайн | BERT без обучения | 0.785 |
| поточечный | Ridge / XGBoost / LightGBM / CatBoost | 0.823–0.825 |
| поточечный | random forest | 0.832 |
| попарный | XGBoost rank:pairwise | 0.834 |
| попарный | **RankNet (MLP)** | **0.844** |
| списочный | ListNet (MLP) | 0.832 |
| списочный | LightGBM LambdaMART | 0.834 |
| списочный | XGBoost rank:ndcg | 0.841 |

1. **BM25 по всем полям — очень сильный бейзлайн.** Обученные модели прибавляют к нему +0,02–0,04. В e-commerce
   поиске точное совпадение слов решает многое.
2. **Попарные и списочные лоссы лучше поточечных** (0,834–0,844 против 0,823–0,832), как и ожидается: они оптимизируют
   порядок. Лучший — RankNet: +0,039 к BM25 (p = 2·10⁻⁷) и +0,012 к лучшей поточечной модели (p = 0,008).
3. **Разброс между фолдами (± 0,013–0,03) сравним с разницей между моделями.** 96 запросов в фолде — мало, поэтому
   выводы делаются по парному тесту на всех 480 запросах, а не по средним.
4. **BERT без дообучения** уступает BM25 (0,785 против 0,805), но как признак добавляет LambdaMART +0,007 —
   статистически незначимо (p = 0,15). Би-энкодер общего назначения не знает, что «ottoman» в мебели — пуф.

### Абляция признаков (LambdaMART)

| набор | NDCG@10 |
|---|---|
| все признаки | 0.834 |
| без BERT | 0.827 |
| без BERT и LSA | 0.821 |
| без признаков класса запроса | 0.807 |
| только lexical | 0.793 |

Самая ценная группа — **класс запроса** (−0,027 без неё): знание, что «salon chair» ищут в категории «Massage Chairs»,
отсекает нерелевантные товары с похожими словами. По важности (gain) лидируют доля слов запроса в названии и похожесть
класса запроса на класс товара.

### DSSM — почему не получилось

DSSM (Huang et al., 2013) — две башни над буквенными триграммами («#ch», «cha», «hai», …): слова хешируются в
триграммы, каждая башня — мешок триграмм → MLP → вектор, оценка — косинус.

- С **раздельными башнями** модель получилась на уровне случайного порядка: до обучения случайные веса проецируют запрос
  и товар в несогласованные пространства (NDCG 0,43), а 384 обучающих запросов мало, чтобы их согласовать — башня
  запросов просто запоминает обучающие запросы (NDCG на train 0,82, на test 0,50).
- С **общей башней** (сиамская сеть) даже необученная модель сравнивает триграммы (0,66), а одна-две эпохи обучения
  дают 0,720 на 5-fold CV — дальше снова переобучение. Это ниже TF-IDF по символьным n-граммам (0,758).

Вывод: нейросетевым текстовым моделям нужны миллионы запросов (DSSM обучали на логах кликов Bing). На маленькой
асессорской разметке их используют иначе — как признак от модели, предобученной на больших данных, или дообучают
готовый BERT как cross-encoder.

## 6. Что можно улучшить

- **Cross-encoder**: дообучить BERT на парах (запрос, товар) из train-фолда — обычно главный прирост в современных
  поисковых системах; на CPU долго.
- Признаки по характеристикам (цвет, материал, размер из запроса ↔ из `product_features`).
- Учесть Partial отдельно: часть «Partial» почти Exact, часть почти мусор.
- Ансамбль RankNet + LambdaMART.

## 7. Вопросы с собеседований

1. **Pointwise, pairwise, listwise — в чём разница?** См. раздел 4.
2. **Почему нельзя просто обучить классификатор релевантности?** Можно (pointwise), но лосс не учитывает, что важен
   порядок внутри запроса и что верх списка важнее низа.
3. **Что такое λ в LambdaMART?** Градиент попарного лосса, взвешенный на |ΔNDCG| от перестановки пары.
4. **Как делить данные?** По запросам (GroupKFold) или по времени, иначе утечка через другие товары того же запроса.
5. **Чем BM25 лучше TF-IDF?** Насыщение по частоте слова и нормировка на длину документа.
6. **Би-энкодер или cross-encoder?** Би-энкодер кодирует запрос и документ независимо — векторы документов можно
   посчитать заранее и искать по ANN-индексу (быстро, для отбора кандидатов). Cross-encoder смотрит на пару целиком —
   точнее, но дорого, используется на последнем этапе для сотни кандидатов.
7. **Как устроен поиск в проде?** Многостадийно: отбор кандидатов (инвертированный индекс BM25 + ANN по эмбеддингам)
   → лёгкое ранжирование → тяжёлое ранжирование (бустинг / cross-encoder) на сотне лучших.
8. **Откуда метки?** Асессоры (точно, дорого) или клики (дёшево, но смещены по позиции — нужна коррекция
   position bias, например, через inverse propensity weighting).
